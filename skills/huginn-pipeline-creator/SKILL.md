# Huginn Pipeline Creator

Create valid, deployable Huginn pipeline folders from a plain English description of what the pipeline should do.

## What This Skill Produces

A complete pipeline folder ready to copy into `~/.huginn/pipelines/`:

```
pipeline-name/
├── manifest.yaml           # Pipeline definition: stages, models, data flow
├── skills/                 # Symlinks or copies of existing skill files
│   ├── 01-stage-name.md
│   ├── 02-stage-name.md
│   └── ...
├── prompts/                # Any additional prompt templates (generated by this skill)
├── files/                  # Reference files the pipeline needs
├── validation/             # Design doc and notes from creation
│   └── design.md
└── README.md               # Human-readable pipeline description
```

## Prerequisites

Before creating a pipeline, the user must have:
1. **Skill files** for each stage — created with the skill-creator or hand-written. Each skill is a `.md` file with YAML frontmatter (name, model, temperature, tools, constraints) and a markdown body containing the system prompt and verification rules.
2. **Knowledge of available models** — what's pulled on their Ollama backends (i3, Mac, etc.)
3. **Reference files** if needed — style guides, example outputs, glossaries, etc.

If the user doesn't have skill files yet, stop and tell them to create skills first using skill-creator, then come back.

## Workflow

### Step 1: Understand the Pipeline Idea

Ask the user to describe:
- What the pipeline does end-to-end (input → output)
- What the stages are (or help them figure this out)
- What skills they already have for each stage
- Where the skill files live on disk
- What models they want per stage (or if you should recommend)
- What reference files are needed
- What backend(s) to use (i3, mac, or both)

Read the `references/manifest-schema.md` file for the exact manifest format, and `references/available-models.md` for model recommendations.

### Step 2: Design the Pipeline

Before writing any files, produce a design summary:

**Pipeline: {name}**
- Description: {what it does}
- Stages: {count}
- For each stage:
  - Name: {stage-name}
  - Skill: {skill filename and path}
  - Model: {model name}
  - Backend: {i3 or mac}
  - Input: {what it reads — $pipeline_input or output from prior stage}
  - Output: {what it produces — filename}
  - Files: {any reference files}
  - Constraints: {network, shell, timeout}

Get the user's approval before proceeding.

### Step 3: Validate Prerequisites

Before generating files, check:
- [ ] Every named skill file exists at the specified path
- [ ] Every referenced model is appropriate for the backend (don't put a 70B model on the i3)
- [ ] Every reference file exists or will be created
- [ ] Stage wiring makes sense (stage N's output matches stage N+1's expected input)
- [ ] No circular dependencies

If anything is missing, tell the user specifically what needs to be created first.

### Step 4: Generate the Pipeline Folder

Create each file in the pipeline folder:

#### manifest.yaml
Read `references/manifest-schema.md` for the exact format. Critical rules:
- `input: $pipeline_input` for the first stage (reads from user-provided input)
- Subsequent stages reference the output filename of the prior stage
- A stage can have multiple inputs as a YAML list
- `on_complete.output_file` names the final deliverable

#### skills/ directory
Copy the user's existing skill files into the pipeline's `skills/` directory, renaming with numeric prefixes for execution order: `01-stage-name.md`, `02-stage-name.md`, etc. The manifest references these local copies.

#### prompts/ directory
If any stage needs a prompt template beyond what's in the skill file, create it here. This is for reusable prompt fragments that multiple skills might reference.

#### files/ directory
Copy or create reference files that skills will read. These get mounted read-only into stage containers.

#### validation/design.md
Write a design document capturing:
- The pipeline's purpose and expected input/output
- Why each model was chosen for each stage
- What each stage does and how they connect
- Known limitations or failure modes
- How to test the pipeline

#### README.md
Short human-readable description of the pipeline, how to run it, and what it produces.

### Step 5: Provide Deployment Instructions

After generating the folder, tell the user:

```bash
# Copy the pipeline to Huginn's home
cp -r {pipeline-name} ~/.huginn/pipelines/

# Verify Huginn sees it
huginn pipelines

# Test with sample input
huginn run {pipeline-name} --input {sample-input-path}

# Check results
huginn status {task-id}
```

## Model Selection Guide

Reference `references/available-models.md` for current model inventory, but the general rules:

| Task Type | Recommended Model | Backend |
|-----------|------------------|---------|
| Classification, routing, yes/no | qwen2.5:0.5b or qwen3:8b | i3 |
| Extraction, analysis | qwen2.5:7b or qwen3:8b | i3 |
| Prose generation, voice matching | qwen3:30b-a3b or qwen3.6:27b | i3 or mac |
| Code review, reasoning | qwen2.5:7b or qwen3:8b | i3 |
| Embeddings | nomic-embed-text | i3 |
| Heavy reasoning, complex output | qwen3.6:27b or llama3.3:70b | mac only |

Rule of thumb: use the smallest model that meets the quality bar for each stage. Classification doesn't need a 27B model. Prose generation in someone's voice does.

## Critical Manifest Rules

These are the most common mistakes — check every manifest against them:

1. First stage MUST have `input: $pipeline_input`
2. Every subsequent stage's `input` must reference a filename that a prior stage's `output` produces
3. If a stage has multiple inputs, use a YAML list
4. `on_complete.output_file` must match the last stage's output filename
5. Every `skill:` path must be relative to the pipeline directory (e.g., `skills/01-analyze.md`)
6. Every `files:` entry must be relative to the pipeline directory (e.g., `files/voice-rules.md`)
7. Constraints default to `network: false, shell: false` — only enable what's needed
8. Model names must match exactly what Ollama reports (e.g., `qwen2.5:7b` not `qwen2.5-7b`)

## Example Interaction

User: "I want a pipeline that takes a security scope document and produces a threat model deliverable"

You should:
1. Ask what skills they have (they might have a stride-analyzer skill, an exec-translator skill, etc.)
2. Ask what models they've pulled
3. Propose stages: scope-parse → threat-enumerate → risk-score → exec-summary → assemble
4. Map skills to stages, identify any gaps
5. Generate the pipeline folder once they approve the design
